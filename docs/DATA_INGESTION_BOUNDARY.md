# Data ingestion boundary

## Purpose

The ingestion layer is the only supported path for external or generated bytes to become Heimdall Electra evidence. It separates source authorization, byte-integrity verification, immutable content-addressed storage, and manifest creation.

It uses Ports and Adapters:

- EvidenceStore is a storage port; FileEvidenceStore is a local adapter.
- ManifestLedger is an audit port; JsonlManifestLedger is a local adapter.
- Source metadata and integrity-verification scheme are explicit input contracts.

A future deployment can replace local adapters with object-lock storage, a signed institutional ledger, a data catalog, or mission transport without changing the ingestion use case.

## Required controls

1. Register and approve the source with owner, terms, permitted evidence class, and permitted verification schemes.
2. Obtain an expected digest from a trusted source or verified signature process before ingest.
3. Preserve original bytes by SHA-256 content address; never overwrite the object.
4. Append a manifest with source, evidence class, digest, size, original name, media type, retrieval time, and verification proof reference.
5. Keep raw evidence and manifests access-controlled and append-only in a production deployment.

## Honesty limits

The local SHA-256 adapter checks that bytes match a supplied digest. It cannot prove who supplied the digest, certify the measurement, or validate the Heimdall Electra physics. It is therefore sufficient only for synthetic fixtures and development integration.

The current CLI intentionally authorizes synthetic input only. No file can be labeled observed through that path. Observed data require a separately reviewed source registration and a stronger approved verification adapter, such as a cryptographically verified provider or instrument signature.
